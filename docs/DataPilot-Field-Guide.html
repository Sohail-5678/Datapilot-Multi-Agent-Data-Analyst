DataPilot, explained from zero.

DataPilot answers business questions about databases in plain English. A team of AI agents plans the question, writes and cross-checks the SQL, runs it safely, draws a chart, and writes an answer in which every number is checked against the real data. This guide walks through what it does, how each piece works, every screen of the app, every tool used, and how to talk about it in an AI engineering interview.

Chapter 01

The idea in one minute

Most of a company's important numbers live in databases. To get them out you have to write SQL, the language databases speak. Most business people can't, so they wait for an analyst.

Large language models (LLMs) like Gemini can write SQL from an English question. The naive version of this, called text-to-SQL, is one prompt that says "here is the database layout, write SQL for this question". It works often, but it fails in ways that are dangerous for business decisions:

  • It picks the wrong table or misspells a value ('Marvel' instead of 'Marvel Comics') and returns nothing or the wrong rows.
  • It writes SQL that runs but answers a slightly different question.
  • When it writes the final sentence, it can invent a number that was never in the data.
  • Nothing stops it from writing DELETE or running a query that scans millions of rows.
The one-sentence pitch

DataPilot replaces "one model makes a guess" with "a team of specialists that plan, double-check each other, run things safely, and prove every number", and it measures how much each specialist helps on a public benchmark.

An analogy that sticks

Think of a small consulting team that gets a question from a manager:

  • A lead reads the question and decides the steps, or asks "what do you mean by best?" if it is vague.
  • A librarian finds which tables and columns matter and how values are spelled.
  • Three analysts each write their own SQL in their own style.
  • A compliance officer refuses anything that isn't a safe read-only query.
  • A reviewer compares the three results. If two agree, that is strong evidence. The reviewer also checks the SQL actually answers the question.
  • A statistician runs Python for things like correlations, in a sealed sandbox.
  • A designer draws the chart, and a writer drafts the answer.
  • A fact-checker verifies every number in the answer against the results and deletes any it can't verify.

That team is exactly what the code builds, using a framework called LangGraph to connect the agents.

Chapter 02

Why this project exists

The product reason

Companies are building "data agents" right now: chat interfaces over their warehouses. The hard part is not getting an LLM to produce SQL; it is making the answer trustworthy enough that a manager can act on it. DataPilot is a working, open, measured version of what those products do internally: verification, safety, human checkpoints and evaluation.

The career reason

It was designed as a portfolio project for AI Engineer and Forward Deployed Engineer roles. Hiring managers for those roles look for four things, and this project shows all four with evidence instead of claims:

Multi-agent orchestration

A supervised LangGraph graph with parallel branches, retries, human-in-the-loop pauses and stop rules.

Harness engineering

Timeouts, budgets, fallbacks between model providers, sandboxed code execution, read-only enforcement, graceful degradation.

Evaluation

A public benchmark (BIRD Mini-Dev), an ablation design, confidence intervals, cost per question, a test suite with hundreds of cases.

Shipping

A deployed, polished product with auth, rate limits, privacy rules and real users' data, at zero cost.

Where it fits: a trio of projects

DataPilot is one of three connected specs. DataPilot (data questions) and ReturnPilot (e-commerce returns) are agents. AgentForge is a planned platform that evaluates, red-teams and optimizes both. They share three contracts so they can work together:

  • trace.v1: the format every run records (which agent did what, which model, how many tokens, how long).
  • profile.v1: the versioned bundle of prompts and routing that AgentForge is allowed to tune. Safety rules are locked out of it.
  • case.v1: the format of a test case, including red-team "seed overrides" such as rows containing prompt-injection text.

Chapter 03

Concepts you need first

Read these once; every later chapter uses them. A longer glossary is at the end.

Database, table, schema

A database is a set of tables (like spreadsheets). The schema is the layout: table names, column names, types and how tables link (foreign keys). DataPilot uses SQLite, a database that lives in a single file.

SQL

The query language. SELECT genre, SUM(total) FROM … GROUP BY genre reads data. Other statements (INSERT, DELETE, DROP) change it, which DataPilot must never do.

LLM

A large language model: predicts text. Here: Google Gemini (Flash, Flash-Lite) and Qwen 27B served by Groq. LLMs are called through APIs and paid per token (roughly ¾ of a word).

Agent

An LLM given one job, specific inputs, and tools or code around it. A multi-agent system wires several agents together so each does one thing well.

LangGraph

A Python framework for building agent workflows as a graph: nodes are steps, edges decide what runs next. It supports parallel branches (Send) and pausing for a human (interrupt()).

Self-consistency (voting)

Generate several answers independently and trust the one most of them agree on. Here: compare the result rows of different SQL queries, not the SQL text.

Grounding

Making sure what the model says is supported by real data. DataPilot's output guard checks every number in the answer against the query results.

Sandbox

A sealed place to run untrusted code. Model-written Python runs in Pyodide (Python compiled to WebAssembly) inside the visitor's browser, with network access removed.

Benchmark and EX

BIRD Mini-Dev is a public set of 500 questions with correct SQL. Execution accuracy (EX) = the share of questions where our SQL returns the same rows as the correct SQL.

Ablation

Turn features on one at a time and measure each one's effect. It tells you which agent is worth its cost.

Chapter 04

One question, start to finish

This is the most important chapter. If you can explain this walkthrough from memory, you understand the project. The question is the demo one, asked on the Chinook music-store database:

The question

"Which 5 genres made the most revenue in 2012, and how did each change vs 2011?"

  1. The browser sends the question

    The workspace posts the question to /api/v1/threads/<id>/ask on the Vercel web app. The web app checks your login, mints a 5-minute signed token (ES256 JWT) and forwards the request to the API on Render. The token proves who you are without the browser ever holding a secret.

  2. The API starts a run and opens a live stream

    FastAPI checks the token, your rate limit and the daily AI quota, then starts the agent graph as a background task. The response is a Server-Sent Events stream: the browser receives events like plan, step, candidate, chosen, table, chart, token, grounding, done as they happen. That is why you see "Agents at work" update live.

  3. Input guard

    The question is checked for prompt-injection attempts ("ignore your instructions…") with Meta's Llama Prompt Guard 2 classifier on Groq plus regex rules. This one is fine, so it passes.

  4. Planner

    Flash-Lite reads a compact summary of the database and returns a JSON plan. Here it produces one step, because one SQL query can compute both years and the change.

    {"needs_clarification": false, "confidence": 0.9, "steps": [{"goal": "Compute total revenue per genre for 2011 and 2012, rank by 2012 revenue, return the top 5 with the change", "needs_sql": true, "needs_chart": true}]}

  5. Schema linker

    Chinook is small (64 columns), so the whole schema goes to the SQL agents, written as compact CREATE TABLE text with sample values. For big databases it ranks columns (BM25 keyword search plus Gemini embeddings), finds join paths through foreign keys, fuzzy-matches literal values in the question (for example "Lewis Hamilton" maps to drivers.forename/surname), and prunes to at most 8 tables and 40 columns.

  6. Two SQL candidates in parallel

    LangGraph's Send launches two branches at once: the direct strategy and the plan-then-SQL strategy, both on Qwen 27B (fast, about 0.3 to 1 second each). Each branch runs its own mini-pipeline: generate SQL, pass the SQL guard, estimate cost with EXPLAIN QUERY PLAN, execute on a read-only connection, and repair up to 2 times on an error or a suspicious empty result.

    SELECT g.Name AS Genre, SUM(CASE WHEN strftime('%Y', i.InvoiceDate)='2012' THEN il.UnitPrice*il.Quantity ELSE 0 END) AS Rev2012, … FROM InvoiceLine il JOIN Invoice i … JOIN Track t … JOIN Genre g … GROUP BY g.Name ORDER BY Rev2012 DESC LIMIT 5

  7. Vote

    Each candidate's result rows are hashed (rows sorted, floats rounded). Both hashes match, so the two independent queries agree. If they had disagreed, the third strategy (few-shot, using similar solved examples) would run and break the tie. This is called adaptive k: it saves about a third of the calls on easy questions.

  8. Verifier

    An LLM reads the question, the candidate SQL and a preview of the rows and answers: do the columns, filters and grouping answer the question? It passes. Confidence becomes High (2 or more agree and the verifier passed). One agreeing candidate plus a pass is Medium; anything else is Low with a "please double-check" note.

  9. Chart agent

    Flash-Lite writes a small Vega-Lite chart spec (a bar chart of Rev2012 by Genre). The spec is checked against a whitelist on the server and again in the browser: no data URLs, no expressions. The browser injects the actual rows; the model never supplies data. If the spec fails, rules pick a chart instead.

  10. Narrator

    Writes at most 120 words using only the rows: "The top five genres by 2012 revenue were Rock ($162.36), Metal ($65.34)…".

  11. Output grounding guard

    Every number in the draft is extracted and must equal a value in the results, or a derivation the code computes itself (difference, percent change, ratio, sum, share), at the precision it was written with. A bad number gets one rewrite, then its sentence is removed and the UI says so. Here all 11 numbers check out, so the badge reads "Numbers checked against results ✓ · 11".

  12. Done: saved and traced

    The run, its spans (a timing record per step, in trace.v1 format), the result rows and the answer are saved to Postgres. The browser shows the answer card with tabs. Real production numbers for this question: 6 LLM calls, about 10,500 tokens, 11 seconds, list-price cost about $0.003.

Two other paths you should know

Human checkpoints. "Show me the best players" is vague, so the planner pauses the graph with LangGraph's interrupt() and shows clickable options. After you pick one, the SQL would scan 183,978 rows of Player_Attributes (above the 100,000 limit), so it pauses again: "Run this query?" with Run anyway / Narrow it down / Cancel.

Python analysis. "Is there a correlation between track length and price?" makes a 2-step plan: SQL fetches the columns, then the analyst writes pandas code. The graph pauses, the browser runs the code in Pyodide and posts the result back, and the graph resumes. Answer: Pearson r = 0.93 across 3,503 tracks.

There are three running parts: the web app in your browser and on Vercel, the API with the agents on Render, and the databases. Plus the external AI providers.

How live progress works

A question can take 5 to 40 seconds and may pause for a human. So the API runs each question as a background task that appends events to a replayable log. The browser reads the log over SSE. If the connection drops (Vercel cuts serverless responses after a time limit), the browser reconnects with GET /v1/runs/<id>/events?after=N and continues where it left off. Pauses for clarify, confirm and the sandbox wait on a future that the matching POST endpoint resolves: humans get 15 minutes, the browser sandbox 60 seconds.

Chapter 07

Safety and trust layers

Interviewers love this chapter, because it shows you think about what can go wrong. Each layer is independent, so one bug doesn't break safety.

Read-only, three ways

  1. Parser guard (sqlglot). Exactly one statement; root must be SELECT or WITH…SELECT; no INSERT/UPDATE/DELETE/DROP/ALTER/CREATE/ATTACH/PRAGMA; no load_extension, readfile, writefile; only known tables; recursive CTEs need a real bound; unconditioned cross joins of big tables (including the sneaky JOIN … ON TRUE) are rejected; non-canonical Unicode is rejected.
  2. Read-only engine. SQLite opened with mode=ro&immutable=1, PRAGMA query_only=ON, and an authorizer callback that allows only read actions. The tests call the executor directly with DELETE and DROP and check the file hash is unchanged.
  3. Read-only files. The database files are chmod a-w in the Docker image.

A real story you can tell

During production testing, a dataset's true West-region total was $13,469.75 but the narrator wrote $13,469.80. The original guard allowed 0.5% slack, so the wrong cents slipped through. The fix was precision-aware matching: a number written to the cent must match to the cent, while honest roundings like "about 13,470" or "$13.5K" still pass. Tests were added for this exact case.

Chapter 09

Your data: uploads

Any signed-in visitor, guests included, can upload their own data and question it with the same agents.

  • Formats: CSV, TSV, TXT (delimiter auto-detected), Excel .xlsx (every sheet becomes a table), JSON (array of objects), SQLite (tables only; views and triggers are never copied). Several files can go into one dataset so they can be joined.
  • Limits: 10 MB per file, 25 MB per dataset, 200,000 rows per table, 100 columns, 12 tables. Guests keep 1 dataset for 1 day; GitHub users 3 datasets for 7 days.
  • Type inference: a column becomes INTEGER, REAL or DATE only if every value fits. $1,234.50 becomes 1234.5, 12% becomes 0.12, mixed date formats become ISO dates.
  • Privacy: uploading requires ticking a consent box, because free-tier Gemini may use prompts to improve its models. Columns that look personal are masked and never sent to the models. Datasets are private to their owner.
  • Why the direct upload: Vercel functions accept at most 4.5 MB of request body, so the browser uploads straight to the API with a token that can only call POST /v1/datasets.
  • Why store it in Postgres: Render's free disk is wiped whenever the instance sleeps, so the built database is kept compressed in Neon and unpacked when needed.
  • Suggested questions: Flash-Lite reads the schema and proposes four questions (ranking, trend, comparison, aggregate), with a rule-based fallback.

How the router decides

  • Routing comes from the profile. profiles/default.json (version 2) says, for each step, a primary model kind and fallbacks: reasoning steps go Flash-Lite → Qwen → Gemini Flash; SQL candidates go Qwen → Gemini Flash.
  • Fail fast. Gemini calls time out after 9 seconds. A 5xx error or timeout skips straight to the next model instead of retrying.
  • Per-model cooldowns. A model that was slow (over 8 s) or overloaded is skipped for 45 seconds, so a slow Flash doesn't block Flash-Lite.
  • Rate-limit aware. On a per-minute 429 it honors the provider's retry-after; on a daily cap it marks that model exhausted for the day.
  • Quota ledger. Requests and tokens per model per day are counted in Postgres. At 90% of a budget the router switches models; when all are exhausted the app goes browse-only with a clear message.
  • Circuit breaker. Five consecutive real failures open a provider for 60 seconds.
  • List-price cost. Each call's tokens are multiplied by the provider's published paid price, so cost is measurable even though the project pays $0.
Why this matters in an interview

You measured that the "best" model (Gemini 3 Flash) was too slow on the free tier, changed the routing in the versioned profile instead of hard-coding it, and added timeouts and cooldowns. That's the kind of production judgment that separates an AI engineer from someone who only calls an API.

Indexes built at startup

  • Value index: distinct values of text columns (up to 50,000 per column, about 12 MB in total) for fuzzy matching literals in questions.
  • Schema index: a description card per column, ranked by BM25 and, when Gemini is available, by embeddings stored in Postgres.
  • Foreign-key graph: NetworkX graph of tables for join paths, including relationships inferred from matching key names.
  • Verified-SQL cache: High-confidence and thumbs-up answers are stored; a near-identical later question reuses the SQL as one extra candidate that still has to win the vote.

Chapter 12

Benchmarks and evaluation

BIRD Mini-Dev is a public text-to-SQL benchmark: 500 questions over 11 real-world databases, each with a correct ("gold") SQL query, an optional "evidence" hint, and a difficulty label.

  • Fixed subset: 150 questions, stratified by database and difficulty with seed 13 (bench/subset_150.jsonl).
  • Splits: 50 train, 50 validation, 50 test. The test split is never used for tuning; few-shot examples come only from train.
  • Metric: execution accuracy, using BIRD's official rule: the set of predicted rows equals the set of gold rows, both run on the same database file.
  • Self-test: with the gold SQL fed in as the "prediction", the harness scores 150/150, proving the scoring path itself is correct.

Chapter 19

Interview questions

Practice answering out loud, then open each one to compare.

Why not just use one LLM call?

One call has no way to know it's wrong. Splitting the work gives checkpoints: linking reduces wrong-table errors, multiple candidates let independent queries vote on the result, repair uses the real database error, and the verifier checks intent. The ablation measures what each piece adds and costs.

Why vote on results instead of SQL text?

Two different SQL queries can be equally correct. What matters is whether they return the same rows. Hashing sorted, rounded rows makes the comparison order-insensitive unless the query is a ranking (ORDER BY with LIMIT).

How do you stop the system from deleting data?

Three independent layers: a sqlglot parser guard that allows only one bounded SELECT, a SQLite connection that is read-only with an authorizer allowing only reads, and read-only database files. Tests call the executor directly with DELETE and DROP and confirm the file hash didn't change.

How do you prevent hallucinated numbers?

The output guard extracts every number and requires it to match a result value or a code-computed derivation at the written precision. Unsupported numbers trigger one rewrite, then removal with a visible notice. Only checked text is streamed. In production it caught $13,469.80 written for $13,469.75 after I tightened the matching rule.

Why run Python in the browser?

Running model-written code on the server is a security risk. Pyodide runs Python as WebAssembly inside a Web Worker on the user's machine, where I remove network APIs before user code runs and kill the worker after 10 seconds. It costs nothing and keeps the server safe.

How does human-in-the-loop work technically?

LangGraph's interrupt() pauses the graph and checkpoints its state. The API emits a clarify_request or confirm_request event and waits on a future. When the user clicks, a POST resolves it and the graph resumes with Command(resume=value).

How did you evaluate it?

On BIRD Mini-Dev with a fixed stratified 150-question subset and a held-out 50-question test split, scored by execution accuracy with BIRD's official set comparison, reported with 95% bootstrap confidence intervals and list-price cost. An oracle self-test scoring 150/150 verifies the scoring path.

What was the hardest production problem?

Free-tier latency. Gemini 3 Flash took 11–25 seconds per call. I measured it from the traces, moved reasoning steps to Flash-Lite in a new profile version, and added 9-second timeouts and per-model cooldowns so a slow model is skipped for 45 seconds. Answers went from over a minute to about 5–30 seconds.

How do you handle provider outages and rate limits?

Each step has a fallback chain. The router honors retry-after on per-minute limits, marks a model exhausted on daily caps, cools down slow or overloaded models, opens a circuit breaker after 5 failures, and keeps a daily quota ledger in Postgres. When everything is exhausted the app degrades to browse-only with a clear message.

How do you deal with personal data?

Columns that look personal are tagged; they're masked in UI samples and excluded from prompts and value links. Traces are redacted before export. Uploads require consent because free-tier providers may train on prompts.

How does the web app talk to the API securely?

The browser never holds a secret. The Next.js server reads the session and mints a 5-minute ES256 JWT for each request. The API has only the public key, so a leaked API config can't mint tokens. Uploads use a separate token scoped to one route.

What is schema linking and why does it matter?

Finding which tables, columns and exact values the question refers to. Most text-to-SQL errors are wrong columns or misspelled values. I use BM25 and embeddings over column descriptions, fuzzy matching against real distinct values, and shortest join paths in the foreign-key graph.

Why LangGraph and not a simple loop?

I needed parallel branches, cycles for repair, pauses for humans and the browser, and resumable state. LangGraph gives those as primitives (Send, conditional edges, interrupt(), checkpointers) and the graph structure is easy to reason about and test.

How would you scale it to many users or real customers?

Stateless API replicas with a Postgres checkpointer and a shared event log, a queue for long analyses, a result cache, per-tenant credentials in a vault for real warehouses, read replicas, and warehouse dry-run cost limits instead of SQLite EXPLAIN.

What would you measure next?

The full C0–C4 ablation and its accuracy-versus-cost curve, then failure categories (wrong join, wrong filter, wrong grain) to decide which agent to improve. A paired McNemar test against main is how AgentForge would gate pull requests.

How did you test something nondeterministic?

A scripted fake LLM returns fixed replies per step, so every graph path is deterministic in tests. Real model quality is measured separately by the benchmark, not by unit tests.
